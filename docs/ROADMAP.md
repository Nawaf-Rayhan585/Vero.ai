# Vero.ai — Roadmap

**This is the official roadmap.** It supersedes any prior phase list or roadmap draft produced before this specification was recorded.

## Phases

| Phase | Scope |
|---|---|
| 0 | Product definition, architecture, scope, development rules *(this documentation)* |
| 1 | Clean project foundation and scaffolding |
| 2 | FastAPI + PostgreSQL backend foundation |
| 3 | Desktop application architecture and dashboard foundation |
| 4 | CCTV/RTSP camera manager |
| 5 | AI detection + tracking engine |
| 6 | People counting + entry/exit analytics |
| 7 | Zones + heatmaps |
| 8 | Vehicle detection/counting + OCR + QR + barcode |
| 9 | Events + analytics system |
| 10 | Authentication + organizations + locations |
| 11 | 3-day trial + subscription/licensing architecture |
| 12 | Own Hardware plan implementation |
| 13 | Vero Cloud infrastructure |
| 14 | Cloud cost/unit economics + pricing model |
| 15 | PayPal subscription integration |
| 16 | Production packaging + automatic service management |
| 17 | Security + performance hardening |
| 18 | Full testing |
| 19 | Private beta |
| 20 | Vero.ai V1 launch |

Future V2 features (dwell time, queue detection, PPE, fire/smoke, license plate recognition, etc. — full list in [V1-SCOPE.md](V1-SCOPE.md)) are not part of this roadmap unless explicitly moved into it later.

## Current status

**Phases 0-8 are accepted by the owner.** **Phases 9-16 (events + analytics; authentication + organizations + locations; 3-day trial + subscription/licensing architecture; Own Hardware plan implementation; Vero Cloud infrastructure; cloud cost/unit economics + pricing model; PayPal subscription integration; production packaging + automatic service management) are implemented and awaiting owner verification** — none is marked complete until the owner has verified it (Development Rule 6). Phase 14 is a documentation/analysis deliverable, not code — see its entry below for what "verification" means for it. Phase 15 is Own Hardware billing only, sandbox only (see its entry below for exactly what that does and doesn't cover) — Vero Cloud billing is a separate, deferred phase. **Phase 16's actual installer build + real Windows Service registration was deliberately not run on this shared dev machine** — every packaging script was written and, where safely possible, tested for real against genuine EDB PostgreSQL binaries (see its entry below); the final "build the .msi and install it" step needs your explicit go-ahead first. Phase 17 has not started.

### What exists today

- `backend/` — FastAPI + SQLAlchemy 2 (sync) + Alembic + PostgreSQL 16. Layout: `main.py` and `app/` (`config`, `database`, `models`, `schemas`, `crypto`, `security`, `auth`, `auth_schemas`, `subscription_schemas`, `device_schemas`, `detection_runner`, `camera_testing`, `tracking`, `counting`, `zones`, `heatmap`, `modules`, `scanning`, `events`, `analytics`, `routers/auth`, `routers/organizations`, `routers/locations`, `routers/members`, `routers/subscription`, `routers/devices`, `routers/jobs`, `routers/cameras`, `routers/tracking`, `routers/lines`, `routers/zones`, `routers/events`, `routers/analytics`, `cloud_routing`, `paypal_client`). Every endpoint now requires a signed-in user and is scoped to one organization (`X-Organization-Id` header, defaulting to the caller's only membership) — the two exceptions are `GET /health`/`GET /health/db` (still public) and `POST /auth/{register,login,refresh}` (public by design; a registered user still authenticates through them). New endpoints: `POST /auth/{register,login,refresh,logout,change-password}`, `GET /auth/me`, `/organizations` (list/create/rename), `/locations` (list/create/rename/delete-or-409-if-it-has-cameras), `/members` (list/add-existing-account-by-email/change-role/remove-or-leave), `/subscription` (`GET` for any member; `PATCH`, Owner-only) plus `/subscription/paypal/*` (Phase 15, see below), `/devices` (list/create/rename/delete — Phase 12, see below). Twelve tables now (`devices` added this phase) and ten migrations. Passwords are hashed with Argon2id (`argon2-cffi`, rehashed on login if parameters change, a dummy hash compared for unknown emails so timing doesn't reveal who has an account); sessions are a short-lived signed JWT access token (`PyJWT`, `HS256` pinned, issuer/audience/`jti` checked) plus a 256-bit random refresh token stored only as a SHA-256 hash, rotated on every use — presenting an already-used refresh token is treated as theft and revokes every session for that user. Roles are Owner/Admin/Member (only an Owner grants Owner; an organization's last Owner can't be removed or demoted); Member is read-only, Admin/Owner can configure. The very first account ever to register adopts every pre-existing (pre-Phase-10) camera and job into its new organization, grouping cameras into one `Location` per distinct old `location_label` value. **Phase 11:** every organization gets a 3-day trial the moment it's created (`Subscription.trial_ends_at`, `app/config.py`'s `trial_days`, default 3); the *growth* subset of configure actions (create/edit a camera, line, zone, location or member; start tracking) additionally requires an active subscription (`require_active_configurator`, 402 once expired) — *shrink* actions (delete anything, stop tracking, remove/leave a member) and all reads stay unaffected regardless of billing status, via the unchanged `require_configurator`. A nullable `plan_type` (`own_hardware`/`vero_cloud`) and an entitlement mechanism (`Subscription.max_cameras`, enforced by `create_camera`) exist as real, tested code but nothing sets a limit on any real organization — Phase 14 decides actual numbers. An Owner-only manual override (`PATCH /subscription`) is also always available to set a subscription's status directly or extend a trial (real PayPal billing arrived in Phase 15, below, but the override remains as an admin/support fallback). **Phase 12** (Own Hardware plan implementation): most of what the plan actually is — local camera manager, local AI, local accounts, local licensing check — was already built across Phases 1-11; the one new concept is device entitlement (`PROJECT.md`: "possibly device entitlement"). Each organization can register/rename/remove `Device` rows (`/devices`) — deliberately just a name someone types (e.g. "Warehouse PC"), no hardware fingerprinting, nothing checking that traffic actually comes from a registered machine. Registering/renaming a device is a *growth* action (`require_active_configurator`, same bucket as adding a location); removing one is not. `Subscription.max_devices` mirrors `max_cameras` — a real, tested entitlement-limit mechanism, unset on every organization today. **Phase 13** makes `plan_type == "vero_cloud"` real: `app/cloud_routing.py`'s `is_cloud_organization(ctx)` checks it, and the two settings `cloud_engine_base_url`/`cloud_engine_internal_secret` (both optional — unset by default, so every existing dev/test setup needs no new `.env` values) tell backend where to reach the new `cloud-engine/` service. The four `routers/tracking.py` endpoints and `routers/cameras.py`'s `test_camera_connection`/`get_camera_snapshot` each gained one new branch, added immediately after the existing camera lookup: a Vero Cloud organization's request is forwarded to `cloud-engine` (`proxy_to_cloud_engine`, an internal-secret-authenticated HTTP call) and its response — JSON or raw JPEG bytes — relayed back verbatim; every other organization's request (still the overwhelming majority — nothing in the existing test suite sets `plan_type`) runs the exact, byte-for-byte unchanged local code below that branch. Cloud-engine isn't configured is a clear `503`, never a silent fallback to local processing. **Phase 15** wires real PayPal billing for the **Own Hardware plan only** (Vero Cloud billing is a separate, deferred phase — its real price is still pending a GPU-cost re-evaluation, per your own instruction for this phase). `app/paypal_client.py` is a thin httpx wrapper around PayPal's REST API (OAuth2 client-credentials token, cached in-memory; Subscriptions v1; Catalog Products v1; Webhooks v1's verify-signature endpoint) — no PayPal SDK dependency, same style as `cloud_routing.py`. Five new endpoints: `POST /subscription/paypal/checkout` (Owner-only — creates a real PayPal subscription against a pre-created plan, stores its id, returns the buyer's approve URL), `POST /subscription/paypal/sync` (Owner-only — re-checks PayPal's own status and updates the local row; this is the phase's actual verified mechanism, not the webhook, since PayPal's real servers can't reach this dev environment's loopback-only backend), `POST /subscription/paypal/cancel` (Owner-only, immediate — no grace period is tracked anywhere in this codebase), `GET /subscription/paypal/{return,cancel-return}` (public, static confirmation pages — deliberately make no database write, since a plain browser redirect carries no proof of identity), and `POST /subscription/paypal/webhook` (public, real signature-verified event handling for `ACTIVATED`/`CANCELLED`/`EXPIRED`, shipped correct but genuinely untestable live here — see "Not verified" below). `Subscription` gained `paypal_subscription_id`/`paypal_plan_id`/`canceled_at` (one new migration); Phase 11's Owner-only manual override still exists unchanged, now explicitly documented as the admin/support fallback alongside real billing rather than its stand-in. A new one-time script, `backend/scripts/setup_paypal_plan.py`, creates the sandbox Product+Plan (a placeholder $19.99/month — Own Hardware's real price is still a separate, pending business decision) and isn't part of the running app. The desktop app opens the PayPal approval URL in the system's default browser via `@tauri-apps/plugin-opener`'s `openUrl()` (already an installed dependency — zero new packages needed), not an embedded PayPal JS SDK button. 740 automated tests now live in `backend/tests/` (720 carried over, 17 new in `tests/test_paypal_subscription.py` mocking `app.paypal_client`'s functions at their call boundary exactly like `test_cloud_routing.py` mocks `httpx.request` — no real PayPal network call is part of the automated suite — plus 3 more the existing route-introspection sweep in `test_tenant_isolation.py` now runs against the 3 new authenticated PayPal endpoints). **Phase 16** fixes the documented CORS gap (`main.py` now also allows `http://tauri.localhost`, where a packaged Tauri build's frontend actually loads from, alongside the existing dev-server origin — both real, both tested directly with an `Origin` header, 3 new tests in `tests/test_health.py`, bringing the suite to **743 automated tests**, all passing clean in one single run) and adds a self-migrating service entrypoint (`backend/service_entrypoint.py`: runs `alembic upgrade head` then execs Uvicorn, so an app upgrade's new migrations apply on every service restart, not just a fragile one-time installer step) and a configurable config-file location (`app/config.py`'s `VERO_CONFIG_PATH` env var, defaulting to today's repo-root `.env` when unset — a packaged install has no repo, so its Windows Service points this at `C:\ProgramData\Vero.ai\config.env` instead; every existing dev/test setup is completely unaffected). See the new `packaging/` entry below for the actual installer machinery this phase builds around those two small, safe backend changes.
- Local PostgreSQL runs via `docker-compose.yml` (development only) on `127.0.0.1:5433`.
- **`cloud-engine/`** (Phase 13) — a second, genuinely separate FastAPI service (`cloud-engine/main.py`), for organizations on the Vero Cloud plan. It is not a copy of `backend/app/tracking.py` (and `counting`/`zones`/`heatmap`/`modules`/`scanning`/`camera_testing`/`crypto`/`events`/`database`/`models`/`schemas`/`config`) — it imports those modules directly, the same `sys.path.insert(0, BACKEND_DIR)` trick `backend/app/detection_runner.py` already uses to import sibling `ai-engine/detector.py`. It shares backend's own PostgreSQL database (`ARCHITECTURE.md`: one shared database, not one per service or per customer) and reads the same repo-root `.env` via `app.config.get_settings()` — there is no separate cloud database, cloud settings module, or new migration. ### Bugs found and fixed during Phase 4 (worth knowing about)

- **OpenCV/FFmpeg silently ignored its own connect/read timeouts** when set via `cv2.VideoCapture()` + `.set(...)` + `.open(...)`, falling back to an internal ~30s default regardless of the requested value. Fixed by using the `cv2.VideoCapture(url, backend, [prop, value, ...])` constructor form instead, which does honor it (confirmed empirically). Also fixed a related bug where the outer "hard timeout" safety net used a `with ThreadPoolExecutor(...):` block, whose `__exit__` blocked on `shutdown(wait=True)` and defeated the timeout entirely by waiting for the abandoned thread anyway.

### Found and fixed during Phase 10 (worth knowing about)

### Found and fixed during Phase 11 (worth knowing about)

- **`SubscriptionRead.model_validate(sub)` failed validation before `is_active` could be added.** The first draft built `is_active` outside the schema (`model_validate(sub).model_copy(update={"is_active": ...})`), but Pydantic v2 requires every non-optional field to already be present on the source object during `model_validate` — it has no way to know a field will be patched in immediately afterward. - **Design decision, not a bug:** which configure actions the trial actually blocks was deliberately split into *growth* (create/edit a camera, line, zone, location or member; start tracking — gated by the new `require_active_configurator`) versus *shrink* (delete anything, stop tracking, remove/leave a member — left on the unchanged `require_configurator`, never blocked). This was the option you chose when asked, and it meant touching only the 9 growth call sites explicitly rather than changing `require_configurator` itself, so every existing delete/stop endpoint's behavior is untouched by construction, not by remembering to carve out an exception.
- **A transaction-atomicity mistake caught before it ran.** The first draft of subscription creation called a helper that committed immediately (`get_or_create_subscription`), invoked from inside `routers/auth.py`'s `register` — which would have split registration's single atomic commit (user + organization + membership + location + subscription, today all-or-nothing) into two, silently changing existing behavior. Caught while re-reading the diff, before running any test: split into a pure, non-committing `new_trial_subscription()` (used by `register`/`create_organization`, which still commit everything together) and a separate `get_or_create_subscription()` that commits immediately only for its own actual use case — self-healing a subscription found missing outside any larger transaction.

### Found and fixed during Phase 16 (worth knowing about)

- **A real security bug, caught by directly testing the secret-generation script rather than trusting it:** `generate_first_run_config.ps1`'s first draft used `[System.Security.Cryptography.RandomNumberGenerator]::Fill(...)` to generate `CAMERA_CREDENTIALS_KEY`/`AUTH_SECRET_KEY`/the Postgres password. That static method doesn't exist under Windows PowerShell 5.1 (the .NET Framework runtime NSIS's bundled PowerShell actually runs, not modern .NET) — and critically, it failed *silently*, producing all-zero-byte keys instead of throwing an error. Every install would have shipped with the exact same, effectively public, "random" secrets. Caught by actually generating a key and inspecting it (`AAAAAAAA...=`), not by assuming the .NET API existed. Fixed with `[System.Security.Cryptography.RNGCryptoServiceProvider]`, verified correct by round-tripping a generated key through Python's real `cryptography.fernet.Fernet` class.
- **A real bug in the Postgres bootstrap script, caught by actually running it against real EDB binaries:** `psql -c "CREATE ROLE ...; CREATE DATABASE ...;"` failed with `ERROR: CREATE DATABASE cannot run inside a transaction block` — `psql -c` wraps multiple `;`-separated statements in one implicit transaction, and `CREATE DATABASE` is one of a handful of Postgres commands that can never run inside one. Fixed by splitting into two separate `psql -c` invocations. Would have made every fresh install's database bootstrap fail on the very first run.
- **A real robustness gap, caught by re-checking rather than assuming a default port is safe:** the first draft hardcoded Postgres's default port 5432 into the generated `DATABASE_URL`. This exact dev machine already has an unrelated service bound to `0.0.0.0:5432`, which would have made the bundled Postgres fail to start on a machine in the same situation. Fixed by probing for a free port (starting at 5432, incrementing until one binds) in `generate_first_run_config.ps1` and threading the chosen port through `init_postgres.ps1`/`register_services.ps1` via the generated config, rather than hardcoding it in three places.
- **Genuinely proven, not just written:** ran the real chain end to end on this machine — `fetch_dependencies.ps1` pulled real EDB PostgreSQL 16.15 binaries and real NSSM; `init_postgres.ps1` ran real `initdb` + created the real `vero` role/database; the backend connected to it and ran all 10 migrations from scratch via `service_entrypoint.py`; Uvicorn served a real `/health` 200. All against a throwaway `C:\ProgramData\Vero.ai`, cleaned up afterward. `verify_portable_python.ps1`'s relocation mechanism was proven with a small stand-in venv (a full production build with the real ~1.4 GB dependency set was also run and is available, but re-verifying relocation with it wasn't repeated — the mechanism being tested is identical regardless of which packages are installed).
- **A concrete demonstration of the "don't touch real system state without asking" boundary, not a bug:** a deliberately safe, throwaway NSSM service-registration test (a harmless service named `VeroAiPackagingSelfTest`, wrapping `timeout.exe`, never started) hit "Administrator access is needed to install a service" — proving the real `VeroAiPostgres`/`VeroAiBackend` registration genuinely does need the elevation `installMode: "perMachine"` requests, exactly as designed. The throwaway service now exists in a stopped, inert, misconfigured state on this dev machine and **could not be removed without admin elevation either** — I deliberately did not trigger a UAC prompt to clean it up without asking first. Removing it needs one of: you approving an elevated PowerShell command (`& "packaging\nssm\nssm.exe" remove VeroAiPackagingSelfTest confirm`), or it can simply be left — it does nothing and starts nothing.
- **A testing-methodology gotcha (this dev machine, not the app):** the `POST /auth/register` proof against the bundled backend first appeared to fail with an unrelated `"username" field required` error — not a Vero.ai schema at all. Cause: `curl` reused a keep-alive connection from earlier, unrelated testing in this same shell session, and this dev machine already has a *different* unrelated service also listening on port 8000 (the same "port 5432/8000 taken by another Docker project" quirk already documented for Postgres — see the port-probing fix above). A specific `127.0.0.1:8000` bind and a wildcard `0.0.0.0:8000` bind from two different processes can coexist on Windows, and a stale reused connection can silently land on the wrong one. Fixed for the retest with `curl -H "Connection: close"`; worth remembering for any future live check on this machine involving port 8000.

- **Vero Cloud's camera ingestion is still direct RTSP, identical to Own Hardware** — `cloud-engine` opens the camera's RTSP URL exactly like `backend` does today, which only works if `cloud-engine` itself has network access to the camera. A real customer's camera sitting behind home/office NAT (the actual point of a "cloud" plan) needs a relay/edge-agent design this phase deliberately deferred (your own choice when asked).
- **`cloud-engine` is single-process, no horizontal scaling** — one `TrackingManager` handling every Vero Cloud camera, the same "no admission control" limitation Own Hardware already has (see below), with no task queue/worker pool to distribute load across instances. Fine for zero real customers; needs revisiting before real Vero Cloud load exists.
- **The internal secret (`CLOUD_ENGINE_INTERNAL_SECRET`) is one static, shared value**, not a per-deployment-rotated credential — adequate for one trusted local pair of processes today, not for a real multi-instance deployment.
- **This phase's live check used direct HTTP requests, not a Playwright browser session** (no browser-automation tool was available in this session) — see the note under "Found and fixed during Phase 13" above. Nothing about this phase's UI itself is unverified (desktop's own 280 tests cover the one copy change), but if a future phase's live-check tooling changes, a browser-driven Vero Cloud walkthrough has still never been done.
- **No physical RTSP camera was tested** (Phases 4-6). All connectivity/snapshot/tracking/counting testing used a genuinely unreachable address (fast-fail path) and synthetic local video files standing in for a readable/moving stream (success path) — OpenCV's open/read logic doesn't distinguish file paths from RTSP URLs internally, so this exercises the real code path, but real-camera specifics (auth negotiation, codecs, vendor quirks, sustained real-world network drops, real pedestrian behavior) are unverified.
- **CPU-only tracking, no admission control.** Confirmed ~0.09s/frame on this dev machine's 4-core CPU (no GPU available to test against); the code doesn't limit how many cameras can be tracked concurrently, so heavy concurrent use is untested.
- **The live counters still reset on every Start; the history lives in events.** The numbers on the AI Modules page and in Live View are per session, but everything counted is also stored as events, so today's totals and trends survive stopping tracking and restarting the backend.
- **Lines cannot be edited after creation.** No drag-to-adjust or reposition — delete and redraw is the only way to change one. A deliberate scope cut for this phase, not a bug.
- **Zones cannot be edited after creation either** — delete and redraw, same deliberate scope cut as lines.
- **A zone's live count is "who is inside right now" only** (no timers — dwell time is V2), and the live heatmap has no reset-while-running control (stop and start again). History is in the zone entered/left events and the saved hourly heat, both on the Analytics page.
- **Zone edge cases were left permissive on purpose.** A person counts as inside by the position of their feet (bottom-center of the box), a point exactly on an edge counts as inside, self-intersecting ("bow-tie") polygons are accepted and follow the even-odd rule, and a zero-area polygon is accepted and simply always reads 0. Say if you'd rather have these rejected at creation.
- **The heatmap measures presence over the whole session, so a person standing still builds heat faster than one walking through.** That is normal heatmap behavior, but it is also why it looks smeared along paths. The heat overlay is rendered by the backend on request (one extra JPEG encode per Live View refresh while the toggle is on), not pre-rendered.
- **Heatmap usefulness on real footage is unverified.** The accumulation and blending are tested, and the live check shows heat trailing real detected people's feet on synthetic panning footage, but how it reads over a busy day of real traffic on a real camera has not been seen.
- **OCR is CPU-heavy and reads the whole frame.** Measured on this dev machine: ~0.65-1.5 s per pass, and while a pass runs YOLO’s per-frame time roughly doubled (157 → 316 ms). Mitigations in place: OCR runs on its own background thread (tracking never waits for it), at most one pass every 5 s (`OCR_INTERVAL_SECONDS`), with ONNX threads capped at 2 (`OCR_THREADS`) — but those numbers are constants I chose, not tuned, and sustained multi-camera load with OCR on is untested. There is no way to limit OCR to a region or zone.
- **Code reading needs the code to be big enough in the frame.** With zxing-cpp, QR / Code 128 / EAN codes about 200 px wide in a 720p frame read; about 120 px did not, and 1D barcodes tilted ~20° were not read (a test pins that a ~60 px barcode is not decoded). Real CCTV placement is the risk; nothing here was tried on a real camera.
- **OCR accuracy on real signage is unverified** beyond the `bus.jpg` photo: English/Spanish Latin text read (“cero”, “emisiones” at 0.99-1.0) but “M1 SOL/SEVILLA” came out as “M15OL/SEUILLA” at 0.84. Other scripts/languages were not tested.
- **The live reads list is deduplicated per session.** A QR/barcode/text value is one entry with a sighting count (a new sighting only after a 5 s gap) and the 50 most recent are shown; each new sighting is also stored as a `read` event.
- **Vehicles: counted, not broken down, and misdetections happen.** Vehicles are car, motorcycle, bus and truck from the same YOLO model, counted at the same lines but separately from people; the box label shows the class, but counts are not split by type. In the real test footage a person was detected as a "bus" for a single frame — flicker like that can create a short-lived spurious vehicle track. Zones and the heatmap remain people-only.
- **Module changes apply on the next Start**, like lines and zones; a running session keeps what it started with (the UI says so).
- **11 new pinned packages:** RapidOCR 3.9.2 + ONNX Runtime 1.30.0 (CPU only, no GPU path) + zxing-cpp 3.1.1 and their small dependencies. RapidOCR’s PaddleOCR models are bundled in its wheel, so nothing downloads at runtime (offline-safe). This adds roughly 40 MB of models plus ONNX Runtime to what Phase 16’s installer will have to ship.
- **Deleting a camera deletes its events and heat history.** Consistent with its lines and zones, and the delete confirmation now says so, but it is a real loss of analytics. Organizations and locations now exist (Phase 10), but this wasn't revisited — deleting a *location* is blocked while it still has cameras (409), but deleting a camera itself still cascades. Say if you would rather camera history be kept.
- **No retention or purge, and growth is unmeasured.** Every event is kept forever. Rows are small (a line crossing is one narrow row), and heat is about 1 KB per camera per hour, but how the table grows over months on a busy camera has not been observed, and the Phase 11/14 plans may want history limits.
- **Events are at-most-once.** They pass through a bounded in-memory queue: a hard crash can lose about the last second, a full queue drops the newest (counted), a database outage is retried but not forever, and an event whose camera was deleted mid-session is dropped. The writer never blocks or crashes tracking. After a crash, the startup step closes sessions at each camera's last event, so uptime is under- rather than over-stated.
- **Zone "entered" counts visits, and the tracker can inflate counts a little.** A person hidden for more than about five seconds and then reappearing counts as entering again (and an exit is recorded when they are lost), and an ID switch by the tracker can add a crossing or a visit. Real footage and real cameras have not been used to see how large this is.
- **Time-zone edge cases.** Charts are cut in the browser's IANA time zone (Postgres does the maths). The repeated hour on the clocks-back day merges into one bucket (24 buckets for a 25-hour day); the skipped hour on the clocks-forward day is not shown. Very long ranges are refused rather than truncated (more than 1,000 buckets).
- **"Tracked" is camera time.** For all cameras it is the sum of camera-seconds, so two cameras running for an hour show two hours, and an hour reads "not running" only if no camera was running in it.
- **The historical heatmap is hour-accurate at its edges and needs the camera to be reachable to sit on a real picture.** Snapshots are hourly, so the hour containing the start of the range is included whole. If the camera does not answer, the heat is drawn on a plain background (and the page says so); heat recorded at a different camera resolution is not mixed in and is reported.
