# Vero.ai — Roadmap

**This is the official roadmap.** It supersedes any prior phase list or roadmap draft produced before this specification was recorded.

## Phases

| Phase | Scope |
|---|---|
| 0 | Product definition, architecture, scope, development rules *(this documentation)* |
| 1 | Clean project foundation and scaffolding |
| 2 | FastAPI + PostgreSQL backend foundation |
| 3 | Desktop application architecture and dashboard foundation |
| 4 | CCTV/RTSP camera manager |
| 5 | AI detection + tracking engine |
| 6 | People counting + entry/exit analytics |
| 7 | Zones + heatmaps |
| 8 | Vehicle detection/counting + OCR + QR + barcode |
| 9 | Events + analytics system |
| 10 | Authentication + organizations + locations |
| 11 | 3-day trial + subscription/licensing architecture |
| 12 | Own Hardware plan implementation |
| 13 | Vero Cloud infrastructure |
| 14 | Cloud cost/unit economics + pricing model |
| 15 | PayPal subscription integration |
| 16 | Production packaging + automatic service management |
| 17 | Security + performance hardening |
| 18 | Full testing |
| 19 | Private beta |
| 20 | Vero.ai V1 launch |

Future V2 features (dwell time, queue detection, PPE, fire/smoke, license plate recognition, etc. — full list in [V1-SCOPE.md](V1-SCOPE.md)) are not part of this roadmap unless explicitly moved into it later.

## Current status

**Phases 0-8 are accepted by the owner.** **Phases 9-11 (events + analytics; authentication + organizations + locations; 3-day trial + subscription/licensing architecture) are implemented and awaiting owner verification** — none is marked complete until the owner has verified it (Development Rule 6). Phase 12 has not started.

### What exists today

- `backend/` — FastAPI + SQLAlchemy 2 (sync) + Alembic + PostgreSQL 16. Layout: `main.py` and `app/` (`config`, `database`, `models`, `schemas`, `crypto`, `security`, `auth`, `auth_schemas`, `subscription_schemas`, `detection_runner`, `camera_testing`, `tracking`, `counting`, `zones`, `heatmap`, `modules`, `scanning`, `events`, `analytics`, `routers/auth`, `routers/organizations`, `routers/locations`, `routers/members`, `routers/subscription`, `routers/jobs`, `routers/cameras`, `routers/tracking`, `routers/lines`, `routers/zones`, `routers/events`, `routers/analytics`). Every endpoint now requires a signed-in user and is scoped to one organization (`X-Organization-Id` header, defaulting to the caller's only membership) — the two exceptions are `GET /health`/`GET /health/db` (still public) and `POST /auth/{register,login,refresh}` (public by design; a registered user still authenticates through them). New endpoints: `POST /auth/{register,login,refresh,logout,change-password}`, `GET /auth/me`, `/organizations` (list/create/rename), `/locations` (list/create/rename/delete-or-409-if-it-has-cameras), `/members` (list/add-existing-account-by-email/change-role/remove-or-leave), `/subscription` (`GET` for any member; `PATCH`, Owner-only). Eleven tables now (`subscriptions` added this phase, one row per organization) and nine migrations. Passwords are hashed with Argon2id (`argon2-cffi`, rehashed on login if parameters change, a dummy hash compared for unknown emails so timing doesn't reveal who has an account); sessions are a short-lived signed JWT access token (`PyJWT`, `HS256` pinned, issuer/audience/`jti` checked) plus a 256-bit random refresh token stored only as a SHA-256 hash, rotated on every use — presenting an already-used refresh token is treated as theft and revokes every session for that user. Roles are Owner/Admin/Member (only an Owner grants Owner; an organization's last Owner can't be removed or demoted); Member is read-only, Admin/Owner can configure. The very first account ever to register adopts every pre-existing (pre-Phase-10) camera and job into its new organization, grouping cameras into one `Location` per distinct old `location_label` value. **Phase 11:** every organization gets a 3-day trial the moment it's created (`Subscription.trial_ends_at`, `app/config.py`'s `trial_days`, default 3); the *growth* subset of configure actions (create/edit a camera, line, zone, location or member; start tracking) additionally requires an active subscription (`require_active_configurator`, 402 once expired) — *shrink* actions (delete anything, stop tracking, remove/leave a member) and all reads stay unaffected regardless of billing status, via the unchanged `require_configurator`. A nullable `plan_type` (`own_hardware`/`vero_cloud`) and an entitlement mechanism (`Subscription.max_cameras`, enforced by `create_camera`) exist as real, tested code but nothing sets a limit on any real organization — Phase 14 decides actual numbers. Since PayPal doesn't exist until Phase 15, an Owner-only manual override (`PATCH /subscription`) is the only way a subscription becomes `active`, `expired` or `canceled`, or a trial gets extended, today. 682 automated tests (pytest, real PostgreSQL, real YOLO/ByteTrack inference, real OpenCV, real Argon2/JWT) live in `backend/tests/`, including a route-introspection sweep that asserts every registered endpoint rejects an anonymous request, and a tenant-isolation matrix that builds a full scenario (camera, lines, zones, events, heatmap) in one organization and checks a second organization gets 404/empty for every read and write against it.
- Local PostgreSQL runs via `docker-compose.yml` (development only) on `127.0.0.1:5433`.
- `ai-engine/` — unchanged from the prototype; tracking, counting, zones, and heatmaps live in `backend/app/` instead (see Phase 5's entry).
- `desktop/` — Tauri v2 + React 19 + TypeScript app shell, now gated on sign-in: signed out shows **Sign in** / **Create account** pages; signed in shows the app shell as before, with the TopBar now naming the current organization and a **Sign out** control. Pages: Dashboard, Detect, Settings, Cameras (location is now a dropdown of the organization's real locations, not free text), **AI Modules** (a per-camera **module selector** — People, Vehicles, Text (OCR), QR codes, Barcodes — saved on the camera and applied the next time tracking starts; Start/Stop tracking, live status + person and vehicle track counts + per-line in/out counts (people, plus vehicles when Vehicles is on), a **Recent reads** list of the QR codes/barcodes/text seen this session, and a **Lines** toggle opening `components/LineEditor.tsx` — click two points directly on the camera's frame to place an entry/exit line, name it, save; existing lines listed with delete), a **Zones** toggle opening `components/ZoneEditor.tsx` (click 3+ points on the camera's frame, undo, finish, name, save; existing zones listed with delete) and a live "N inside" count per zone, **Live View** (the AI-annotated feed also shows each line with its live count and each zone with its live occupancy burned into the video, drawn server-side; while tracking is active a **Show heatmap** checkbox swaps the feed to the same frame with the accumulated heat overlay). **Events** and **Analytics** are real pages (as in Phase 9), and the Dashboard has a **Today** row of tiles. **Account** is a real page too: profile + sign out, change password, an organization switcher/rename/create-another, locations (add/rename/delete), and members (add an existing account by email with a role, change role, remove/leave). **Subscription** is a real page now (Phase 11): status badge, a trial countdown ("N days left" / "Trial ended") computed client-side from the server's `trial_ends_at`, a plan-type selector (Owner-only to change), and — Owner-only, clearly labelled as temporary — a manual override to set status directly or extend the trial, since PayPal doesn't exist until Phase 15. The TopBar also shows a small trial indicator ("Trial: N days left" / "Trial ended — Upgrade") linking to it. Every configuration control on Account and Cameras is hidden for a Member (the API enforces the same rule regardless), and the subset that *grows* usage (Add camera/location/member, Edit, per-row role changes) is additionally hidden once the trial has ended with no active subscription — Delete/Test connection/Remove/Leave stay visible either way, matching the backend's growth/shrink split exactly. The access token lives in memory only (`src/auth/authSession.ts`); the refresh token is kept in the **Windows Credential Manager** via a small Rust command (`src-tauri/src/secure_store.rs`, the `keyring` crate) — outside a real Tauri window (this project's Playwright live-checks, which run against the plain Vite dev server) it clearly falls back to `localStorage` instead. A 401 triggers exactly one silent refresh-and-retry (de-duplicated across concurrent requests) before signing out. 274 automated tests (Vitest + Testing Library, API layer mocked, no backend required) live alongside the source files they test.
- Repo-root `shared/` and `tests/` are still empty placeholders (backend tests live in `backend/tests/`, desktop tests live in `desktop/src/`).
- Still not implemented: license-plate recognition and parking analytics (V2), PayPal/real billing, the Own Hardware and Vero Cloud plans' actual differentiated behavior, real pricing/entitlement numbers, cloud infrastructure, production backend orchestration, a self-contained installer, continuous/background camera connection monitoring, email (so no invitations, email verification, or password reset), MFA/SSO, organization deletion, per-location permissions, an audit log, and rate limiting/lockout on login.
- The Windows installer (`tauri build` → MSI/NSIS) still cannot run standalone on a clean PC: the backend (`uvicorn`) and PostgreSQL must both be started separately, and a packaged build additionally can't reach the backend at all yet (see Open items).

### Bugs found and fixed during Phase 4 (worth knowing about)

- **OpenCV/FFmpeg silently ignored its own connect/read timeouts** when set via `cv2.VideoCapture()` + `.set(...)` + `.open(...)`, falling back to an internal ~30s default regardless of the requested value. Fixed by using the `cv2.VideoCapture(url, backend, [prop, value, ...])` constructor form instead, which does honor it (confirmed empirically). Also fixed a related bug where the outer "hard timeout" safety net used a `with ThreadPoolExecutor(...):` block, whose `__exit__` blocked on `shutdown(wait=True)` and defeated the timeout entirely by waiting for the abandoned thread anyway.
- **A raw `<img src="…snapshot">` never shows a broken camera's real error.** Chromium's Opaque Response Blocking silently drops a non-image (JSON error) body on a cross-origin no-cors image request — the `<img>` element's `onerror` never fires, so the UI would show nothing at all, indefinitely, for an unreachable camera. Confirmed live against a genuinely unreachable address before switching Live View to fetch the snapshot via `fetch()` (a normal CORS-mode request) and rendering it through an object URL instead.

### Bugs found and fixed during Phase 5 (worth knowing about)

- **A background thread's `finally: cap.release()` could crash on `None`.** When the reconnect loop gave up (or was interrupted by `stop()`), `cap` became `None`, and the unconditional `cap.release()` in `TrackingSession._run()`'s `finally` block would raise `AttributeError` in the background thread. Caught before it ever ran, by tracing the give-up/stop paths by hand; fixed with a `None` guard.
- **`status: "running"` doesn't mean a frame has been processed yet.** The tracking loop sets status to `running` as soon as the camera connection opens, but the *first* `model.track()` call pays a one-off ~6-7s warm-up cost (confirmed by direct measurement) before any frame/track data exists. This is real, expected behavior, not a bug — but it did catch out an early version of the AI Modules row logic, and is worth knowing if `frame_count`/`active_track_ids` look like 0 right after starting.

### Testing pitfalls found and fixed during Phase 6 (not application bugs)

- A naive "paste a person crop onto a plain background" synthetic test video produced **zero** YOLO detections — confirmed empirically before relying on it. The working technique instead pans a cropped window across the real `bus.jpg` photo (every pixel stays genuinely real, only what's visible shifts), which reliably produces stable track IDs with monotonically-shifting positions — a real, honest way to test line-crossing end to end without a physical camera.
- The test DB truncation helper (`clean_tables` in `tests/conftest.py`) had to be updated to include the new `lines` table — Postgres refuses to truncate `cameras` alone once another table has a foreign key into it. Anyone adding a new table with a FK to an existing one needs to remember this.

### Found and fixed during Phase 7 (worth knowing about)

- **Heatmap rendering truncated instead of rounding.** The blend ended in `.astype(np.uint8)`, which truncates: a pixel nobody walked near (alpha ~ 0) could come out one level darker than the original whenever float error landed just under its value. Caught while writing the "distant pixel is left exactly alone" test, before running it; fixed with `np.rint(...)` in `app/heatmap.py`.
- **Testing pitfall (tooling, not the app): Playwright cannot read the body of a `fetch()`-made response through a `page.on("response")` listener.** The live check's attempt to save the raw JPEGs the backend served produced zero-byte files. The verification relies on the browser screenshots of Live View instead, which show exactly what the app renders. If raw served frames are ever needed, fetch them with `page.request` rather than sniffing the page's own responses.
- The `panning_video` test fixture moved from `tests/test_tracking_counting.py` into `tests/conftest.py` so the zone/heatmap end-to-end test could share it; `clean_tables` gained `zones` (the same foreign-key lesson as Phase 6).

### Found and fixed during Phase 8 (worth knowing about)

- **A module checkbox could fail to visibly change at the moment of the click.** Found by the live browser check, not by the unit tests: the box’s "just clicked" state came from the save’s pending state, which React Query updates a tick after the click, and a controlled checkbox snaps back to its old value in between (Playwright reported that clicking the checkbox did not change its state). Fixed by holding the click in local state until the save settles (`components/ModuleSelector.tsx`), with a regression test asserting the box is already checked in the same tick as the click — confirmed failing on the old code first.
- **Testing pitfalls (not app bugs).** Never `from tests.conftest import ...`: that re-executes conftest under a second module name, and its top-level code rewrites `DATABASE_URL` (which would point the tests at `<db>_test_test`) — share values through fixtures instead. zxing-cpp’s `|` operator on `BarcodeFormat` is deprecated; pass a list of formats.
- **A wrong claim in my own planning, caught before it reached the docs:** I thought the OCR model garbled accented letters; that was my terminal’s encoding, and the model reads "eléctricamEMTe" correctly.
- Three existing tests that pinned exact response shapes (the camera keys; two line-count dicts) were updated for the new additive fields (`enabled_modules`, `vehicle_in_count`/`vehicle_out_count`). Nothing else in the Phase 1-7 tests changed behavior.

### Found and fixed during Phase 9 (worth knowing about)

- **A phantom hour on the clocks-forward day.** Cutting hourly buckets in PostgreSQL produced a zero-length 02:00 bucket for the local hour that doesn't exist on the day the clocks go forward (24 buckets for a 23-hour day), which a chart would have shown as a spurious "not running" sliver. Caught by a test of New York's 2026 spring-forward day; fixed by skipping zero-length buckets. (The opposite case, the repeated hour on the clocks-back day, merges into one bucket, and is documented below.)
- **Switching camera on Analytics showed the previous camera's totals, undimmed, until the new numbers arrived.** Found by the live browser check (after selecting the Dock camera the tiles still read the Street camera's figures). The chart already dimmed its previous render while loading, but the tiles and breakdown tables did not, so old numbers looked current. Fixed: tiles and tables are dimmed too, and the "nothing was tracked" note is withheld while the numbers are stale; covered by a test.
- **Closing a dangling session was ambiguous and not repeatable.** The startup step that closes a session a crash left "running" stamped its closing event at exactly the last event's time, so the two tied, "the latest uptime event" was ambiguous, and running the step twice closed the session twice. Caught by tests; fixed by stamping it one microsecond later.
- Smaller things found and fixed while testing: a bad (non-database) item in the write queue would have been retried forever and blocked everything behind it — it is now isolated and dropped; a test's dates accidentally straddled the US clock change (test data, not the code).
- **Testing pitfalls (tooling):** the Bash tool fails on long heredocs containing backticks, so multi-line edits were done with patch scripts instead; and the status badges are styled uppercase, so a browser script reading a page's `innerText` sees "TRACKING STARTED" and needs a case-insensitive match.

### Found and fixed during Phase 10 (worth knowing about)

- **A camera's location could appear stale right after changing it.** `expire_on_commit=False` (the existing session setting) meant that after committing a new `location_id`, the already-loaded `camera.location` relationship object still pointed at the old location, so the very next read of the camera you'd just moved showed its old location name. Caught by a test (`assert 'Main location' == 'Warehouse'` failed), fixed with an explicit `db.expire(camera, ["location"])` after a location change.
- **Two access tokens issued for the same user in the same wall-clock second were byte-for-byte identical.** JWT's `exp`/`iat` are whole-second values, discarding the microsecond precision the code actually has, and a refresh-rotation test caught two tokens colliding. Fixed by adding a random `jti` claim (also a legitimate auditability improvement, not just a test workaround), with a regression test.
- **The desktop UI only blocked "Leave" on an organization's last Owner for that Owner removing themself — not an Admin removing them.** The backend's rule ("an organization must always have at least one Owner") applies to any removal, not just self-removal; found by re-reading the backend route before writing the corresponding desktop test, and fixed before it shipped.
- **The Cameras page's "Organization default" location option would have silently done nothing if chosen while editing an existing camera.** The backend's PATCH treats an omitted `location_id` as "leave unchanged", and there is no way for the desktop form to know which location the backend would actually default a *new* camera to (locations are listed alphabetically, not by creation order) — so "Organization default" is now offered only when adding a camera, never when editing one.
- **Switching organizations in the desktop app could show a beat of the previous organization's cameras/events/locations/members.** React Query caches by query key, and none of those keys are organization-scoped, so the cached data from before a switch would render until each query's own refetch caught up. Rather than rewire every existing query key, `AuthContext` now clears the whole query cache whenever the selected organization (or the signed-in identity) actually changes — found and fixed proactively, not by a failing test.
- **Testing pitfalls (not app bugs).** Registering a second account through the test client's `add_member`-style helper made that account a member of *two* organizations (their own, plus the one they were added to), which made `get_org_context`'s "which organization did you mean?" ambiguity check correctly reject requests that didn't specify `X-Organization-Id` — several new tests had to set that header explicitly. `from tests.conftest import TEST_PASSWORD` reproduced the documented `tests.conftest` shadowing gotcha again; fixed by redefining the constant locally, per the standing rule. FastAPI's `app.routes` wraps included routers as opaque objects with no `.methods`/`.path` in this version, so the "every route requires auth" sweep test iterates the original router modules directly instead.
- **Live-check environment notes.** The backend's CORS allowlist is pinned to `http://localhost:1420` (Vite's configured dev port for Tauri), so the live check's Vite instance had to run on that exact port, not an arbitrary one. Vite's dev server binds only to `[::1]` (IPv6), not `127.0.0.1` — reachable at `localhost`, not `127.0.0.1`, despite the "prefer 127.0.0.1" rule elsewhere in this project (that rule is about a different, Docker-port-clash situation). Docker Desktop had crashed unprompted again (the known quirk) and had to be relaunched before the dev database was reachable.
- **A genuinely useful discovery, not a caveat:** the `keyring` crate's Windows Credential Manager integration has no mock for the API version used here, so `cargo test` exercises the *real* OS credential store (a distinct test-only service name and per-test account names, with cleanup) — more verification than the approved plan expected to be possible, not less.
- **A real (not a bug) limitation surfaced by the live check:** being added to an organization is not pushed to that person's already-open session — they see it only after signing out and back in, or after their access token's next silent refresh (which also returns the current membership list). No websocket/poll exists for this yet.

### Found and fixed during Phase 11 (worth knowing about)

- **`SubscriptionRead.model_validate(sub)` failed validation before `is_active` could be added.** The first draft built `is_active` outside the schema (`model_validate(sub).model_copy(update={"is_active": ...})`), but Pydantic v2 requires every non-optional field to already be present on the source object during `model_validate` — it has no way to know a field will be patched in immediately afterward. Fixed before any test ran against it: `is_active` is now a `@computed_field` on `SubscriptionRead` itself, computed from the same shared `is_subscription_active(status, trial_ends_at)` function `require_active_configurator` uses for real enforcement (refactored to take plain values instead of a `Subscription` row, so both the ORM-backed dependency and the Pydantic schema can call the identical logic without duplicating it).
- **Design decision, not a bug:** which configure actions the trial actually blocks was deliberately split into *growth* (create/edit a camera, line, zone, location or member; start tracking — gated by the new `require_active_configurator`) versus *shrink* (delete anything, stop tracking, remove/leave a member — left on the unchanged `require_configurator`, never blocked). This was the option you chose when asked, and it meant touching only the 9 growth call sites explicitly rather than changing `require_configurator` itself, so every existing delete/stop endpoint's behavior is untouched by construction, not by remembering to carve out an exception.
- **A transaction-atomicity mistake caught before it ran.** The first draft of subscription creation called a helper that committed immediately (`get_or_create_subscription`), invoked from inside `routers/auth.py`'s `register` — which would have split registration's single atomic commit (user + organization + membership + location + subscription, today all-or-nothing) into two, silently changing existing behavior. Caught while re-reading the diff, before running any test: split into a pure, non-committing `new_trial_subscription()` (used by `register`/`create_organization`, which still commit everything together) and a separate `get_or_create_subscription()` that commits immediately only for its own actual use case — self-healing a subscription found missing outside any larger transaction.
- **Testing pitfalls (not app bugs).** Desktop: a query for exact text like `"Active"` or `"Trialing"` matched twice once the Subscription page's own manual-override `<select>` (whose `<option>` text is the same words) was on screen — scoped to the status badge's class instead. Two AccountPage/CamerasPage tests clicked a canGrow-gated button synchronously right after awaiting an *unrelated* query (the members/locations list, not the separate subscription fetch) — a genuine race that happened to not flake locally but was fixed to `await screen.findByRole(...)` regardless, the same lesson Phase 10 already documented for a different pair of queries.

### Open items needing an owner decision

- **PostgreSQL for the Own Hardware plan.** The spec mandates PostgreSQL project-wide and that end users never run Python/Uvicorn manually. Phases 12 and 16 must decide how a customer's machine gets PostgreSQL (a managed local instance installed and supervised by the installer, or the local engine syncing to a cloud PostgreSQL only). Not decided in Phase 2.
- **Packaged app can't reach the backend.** A production Tauri build loads from `http://tauri.localhost`, but the backend's CORS only allows `http://localhost:1420` (the dev server origin). Only affects `npm run tauri build` output, not `npm run tauri dev`. Belongs to Phase 16/17.
- **Video job results are still one JSONB value per job** (the Detect prototype page). The roadmap had pointed this redesign at Phase 9; you chose to defer it, since Detect is the pre-V1 prototype and is not in V1's feature list. Revisit if the page survives to launch.
- **Accounts/organizations live in this same local backend and PostgreSQL, not a separate cloud service.** `ARCHITECTURE.md`'s target diagram puts Auth in "Vero.ai Cloud", used by both the Own Hardware and Vero Cloud plans — that cloud doesn't exist until Phases 12/13, so Phase 10 built accounts as a local-backend feature (in its own modules, `app/security.py`/`app/auth.py`, so they can move later). This was flagged as an assumption, not decided as an architecture choice — Phases 12/13 need to decide whether Own Hardware accounts stay local, move to the cloud, or sync between the two, and what happens to a Own Hardware customer's local accounts when that decision lands.
- **No email service exists, so there is no email verification, no password reset, and no invitation email** — adding someone to an organization requires they already have an account (by email), and there is no way to recover a forgotten password except changing it while signed in. Needs a decision on which phase adds email (and which provider).
- **No rate limiting or lockout on login/register/refresh.** A determined attacker with network access could brute-force a password; the backend currently only listens on loopback, and this was explicitly scoped to Phase 16/17 per the approved Phase 10 plan.
- **Email addresses are unique across the whole `users` table, not per organization.** One person's email identifies one account across every organization they belong to — intentional (there is one login, not one per organization), but worth confirming it matches the intended multi-tenant model.
- **A stolen access token is usable until it expires** (~15 minutes by default) — there is no server-side access-token revocation, only refresh-token revocation. Acceptable for a short-lived token, but worth stating plainly given camera credentials and analytics are behind it.
- **There is no automated way for a subscription to become `active` yet.** Only the Owner-only manual override (`PATCH /subscription`) can do it, until Phase 15 ships PayPal. This is by design for Phase 11, but means every real trial ends in `expired` unless you (or an Owner) intervene by hand — worth confirming that's acceptable for however long Phase 15 is away.
- **Whether 3 days is the right trial length is a business question, not a technical one** — it's a config default (`TRIAL_DAYS`), trivial to change, but I have no basis to judge if it converts well.
- **`canceled` and `expired` behave identically today** (both block growth actions) — there's no distinct "you canceled, here's what happens to your data" flow, since that's a billing-system concern (Phase 15).
- **Changing a member's role was included in the "growth" (trial-gated) actions**, alongside adding a member — debatable, since a role change doesn't add headcount. Say if you'd rather it behaved like removal (always allowed).
- **The entitlement mechanism (`max_cameras`) is real and tested but inert** — every organization's limit is `None` (unlimited) today; only Phase 14's pricing model would ever set a real number, and only camera count is stubbed (not module count, device count, or anything else `PROJECT.md` mentions as a possible limit).
- **No physical RTSP camera was tested** (Phases 4-6). All connectivity/snapshot/tracking/counting testing used a genuinely unreachable address (fast-fail path) and synthetic local video files standing in for a readable/moving stream (success path) — OpenCV's open/read logic doesn't distinguish file paths from RTSP URLs internally, so this exercises the real code path, but real-camera specifics (auth negotiation, codecs, vendor quirks, sustained real-world network drops, real pedestrian behavior) are unverified.
- **CPU-only tracking, no admission control.** Confirmed ~0.09s/frame on this dev machine's 4-core CPU (no GPU available to test against); the code doesn't limit how many cameras can be tracked concurrently, so heavy concurrent use is untested.
- **The live counters still reset on every Start; the history lives in events.** The numbers on the AI Modules page and in Live View are per session, but everything counted is also stored as events, so today's totals and trends survive stopping tracking and restarting the backend.
- **Lines cannot be edited after creation.** No drag-to-adjust or reposition — delete and redraw is the only way to change one. A deliberate scope cut for this phase, not a bug.
- **Zones cannot be edited after creation either** — delete and redraw, same deliberate scope cut as lines.
- **A zone's live count is "who is inside right now" only** (no timers — dwell time is V2), and the live heatmap has no reset-while-running control (stop and start again). History is in the zone entered/left events and the saved hourly heat, both on the Analytics page.
- **Zone edge cases were left permissive on purpose.** A person counts as inside by the position of their feet (bottom-center of the box), a point exactly on an edge counts as inside, self-intersecting ("bow-tie") polygons are accepted and follow the even-odd rule, and a zero-area polygon is accepted and simply always reads 0. Say if you'd rather have these rejected at creation.
- **The heatmap measures presence over the whole session, so a person standing still builds heat faster than one walking through.** That is normal heatmap behavior, but it is also why it looks smeared along paths. The heat overlay is rendered by the backend on request (one extra JPEG encode per Live View refresh while the toggle is on), not pre-rendered.
- **Heatmap usefulness on real footage is unverified.** The accumulation and blending are tested, and the live check shows heat trailing real detected people's feet on synthetic panning footage, but how it reads over a busy day of real traffic on a real camera has not been seen.
- **OCR is CPU-heavy and reads the whole frame.** Measured on this dev machine: ~0.65-1.5 s per pass, and while a pass runs YOLO’s per-frame time roughly doubled (157 → 316 ms). Mitigations in place: OCR runs on its own background thread (tracking never waits for it), at most one pass every 5 s (`OCR_INTERVAL_SECONDS`), with ONNX threads capped at 2 (`OCR_THREADS`) — but those numbers are constants I chose, not tuned, and sustained multi-camera load with OCR on is untested. There is no way to limit OCR to a region or zone.
- **Code reading needs the code to be big enough in the frame.** With zxing-cpp, QR / Code 128 / EAN codes about 200 px wide in a 720p frame read; about 120 px did not, and 1D barcodes tilted ~20° were not read (a test pins that a ~60 px barcode is not decoded). Real CCTV placement is the risk; nothing here was tried on a real camera.
- **OCR accuracy on real signage is unverified** beyond the `bus.jpg` photo: English/Spanish Latin text read (“cero”, “emisiones” at 0.99-1.0) but “M1 SOL/SEVILLA” came out as “M15OL/SEUILLA” at 0.84. Other scripts/languages were not tested.
- **The live reads list is deduplicated per session.** A QR/barcode/text value is one entry with a sighting count (a new sighting only after a 5 s gap) and the 50 most recent are shown; each new sighting is also stored as a `read` event.
- **Vehicles: counted, not broken down, and misdetections happen.** Vehicles are car, motorcycle, bus and truck from the same YOLO model, counted at the same lines but separately from people; the box label shows the class, but counts are not split by type. In the real test footage a person was detected as a "bus" for a single frame — flicker like that can create a short-lived spurious vehicle track. Zones and the heatmap remain people-only.
- **Module changes apply on the next Start**, like lines and zones; a running session keeps what it started with (the UI says so).
- **11 new pinned packages:** RapidOCR 3.9.2 + ONNX Runtime 1.30.0 (CPU only, no GPU path) + zxing-cpp 3.1.1 and their small dependencies. RapidOCR’s PaddleOCR models are bundled in its wheel, so nothing downloads at runtime (offline-safe). This adds roughly 40 MB of models plus ONNX Runtime to what Phase 16’s installer will have to ship.
- **Deleting a camera deletes its events and heat history.** Consistent with its lines and zones, and the delete confirmation now says so, but it is a real loss of analytics. Organizations and locations now exist (Phase 10), but this wasn't revisited — deleting a *location* is blocked while it still has cameras (409), but deleting a camera itself still cascades. Say if you would rather camera history be kept.
- **No retention or purge, and growth is unmeasured.** Every event is kept forever. Rows are small (a line crossing is one narrow row), and heat is about 1 KB per camera per hour, but how the table grows over months on a busy camera has not been observed, and the Phase 11/14 plans may want history limits.
- **Events are at-most-once.** They pass through a bounded in-memory queue: a hard crash can lose about the last second, a full queue drops the newest (counted), a database outage is retried but not forever, and an event whose camera was deleted mid-session is dropped. The writer never blocks or crashes tracking. After a crash, the startup step closes sessions at each camera's last event, so uptime is under- rather than over-stated.
- **Zone "entered" counts visits, and the tracker can inflate counts a little.** A person hidden for more than about five seconds and then reappearing counts as entering again (and an exit is recorded when they are lost), and an ID switch by the tracker can add a crossing or a visit. Real footage and real cameras have not been used to see how large this is.
- **Time-zone edge cases.** Charts are cut in the browser's IANA time zone (Postgres does the maths). The repeated hour on the clocks-back day merges into one bucket (24 buckets for a 25-hour day); the skipped hour on the clocks-forward day is not shown. Very long ranges are refused rather than truncated (more than 1,000 buckets).
- **"Tracked" is camera time.** For all cameras it is the sum of camera-seconds, so two cameras running for an hour show two hours, and an hour reads "not running" only if no camera was running in it.
- **The historical heatmap is hour-accurate at its edges and needs the camera to be reachable to sit on a real picture.** Snapshots are hourly, so the hour containing the start of the range is included whole. If the camera does not answer, the heat is drawn on a plain background (and the page says so); heat recorded at a different camera resolution is not mixed in and is reported.
- **Not verified:** long-running operation (days of continuous events, real database growth, the recorder under sustained load), real cameras and real traffic, and how the charts read over a genuinely busy period. The pages poll every 5-10 seconds; there is no push.
- **Not verified (Phase 10):** the Windows Credential Manager path *inside a real packaged Tauri window* — it is genuinely unit-tested (`cargo test` against the real credential store, see above) and compile-checked, but the live browser check necessarily used the plain-browser `localStorage` fallback, since Playwright drives a normal browser, not a Tauri webview. Real multi-machine use (two different Windows accounts/machines sharing an organization) and brute-force resistance (no rate limiting yet) are also unverified.
- **Not verified (Phase 11):** what happens over a genuinely long trial period (weeks/months of an organization sitting `expired`) — the live check exercises the transition instantly via the manual override, not real elapsed time. Real customer reaction to trial expiry, and whether 3 days is long enough to evaluate the product, are unknowable without real users.
